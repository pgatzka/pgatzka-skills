# Build tools

## Overview

Personal conventions for invoking build tools from inside a Claude Code session. Three principles:

1. **Never build unless required.**
2. **Generated code is never checked into git.**
3. **A build invocation should do only the work the goal needs** — no `clean`, no tests on compile-checks, no publish / docs / signing / dependency refresh by default.

Rules are written tool-agnostically; per-tool notes give the concrete commands. If the project's build tool isn't covered here, ASK before guessing the right invocation.

## Rules

### 1. Don't build unless required

Build is required when:

- **The user explicitly asks** — phrases like "build", "compile", "package", "install", or directly running a build command.
- **Verification needs it.** Before claiming a code change is done, a change that affects compilation or runtime has to compile (mirrors the `verification-before-completion` discipline). Don't claim a Java refactor is complete without compiling; don't claim a TS change is done without `tsc` / a build.
- **Dependencies changed.** After editing `pom.xml`, `build.gradle(.kts)`, `settings.gradle`, `package.json`, `Cargo.toml`, `go.mod`, `requirements.txt`, `pyproject.toml`, or any other manifest, build to confirm resolution still works.

Build is NOT required when:

- The user is exploring or asking a question that reading the code already answers.
- Nothing changed since the last successful build.
- A "maybe broken" hunch isn't backed by a specific reason. Don't build defensively — diagnose first.

If you're not sure whether a build is required, ASK rather than running one speculatively. Every build burns time and wall-clock that the user notices.

### 2. Generated code is never checked into git

Build outputs, compiled artifacts, and tool-generated sources belong outside version control. They get regenerated by the build; they don't belong in `git log` or in code review.

Common generated paths to gitignore:

| Tool | Paths |
|---|---|
| Maven | `target/` |
| Gradle | `build/`, `.gradle/` |
| Java (any) | `*.class`, `out/`, `bin/` (when not a checked-in source dir) |
| npm / pnpm / yarn | `node_modules/`, `dist/`, `build/`, `.next/`, `.nuxt/`, `coverage/` |
| Cargo | `target/` |
| Go | binaries (no fixed dir; gitignore by name) |
| Python | `__pycache__/`, `*.pyc`, `.venv/`, `dist/`, `build/`, `*.egg-info/` |

When adding any of these, invoke the `gitignore` skill — it governs the conventions (anchor with leading `/` for top-level, alphabetical placement, no speculative bulk-adds, only add what actually exists in the repo).

If generated code is currently checked in (someone committed `target/` or `dist/`), flag it and ASK before removing — the cleanup is a deliberate change with PR implications, not a silent fix.

**Exceptions** that genuinely belong in git:

- Lockfiles: `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock` (for binaries), `go.sum`. These are not "generated code" — they're inputs to reproducible builds.
- Generated sources that the project deliberately commits as the source of truth (rare; ASK before assuming).

### 3. A build invocation should do only the work the goal needs

Default to the smallest invocation that accomplishes the goal. Adding phases costs time and rarely catches anything the smaller invocation wouldn't.

#### Skip `clean` unless build state is genuinely suspect

Don't reach for `clean` reflexively. Modern build tools have correct incremental compilation; a fresh `clean` rarely fixes anything that wasn't already broken.

`clean` is justified when:

- A dependency was *removed* (the cached classpath / `node_modules` may still resolve it).
- Generated sources are stale and the tool can't tell.
- An incremental-compile failure you can't otherwise explain ("it worked on `clean`" is a real signal — but rare).

Otherwise: incremental.

#### Skip tests on iterative compile-checks

When the goal is "does this compile?" — get the fast feedback first, then run tests separately when the user asks or before claiming done.

| Tool | Compile without tests |
|---|---|
| Maven | `mvn compile` (sources only), `mvn package -DskipTests` (full package, no test exec), `mvn install -DskipTests` |
| Gradle | `./gradlew compileJava` (sources only), `./gradlew build -x test` (full build, no test exec), `./gradlew assemble` (build outputs without test compile) |
| npm / pnpm / yarn | `npm run build` (typically excludes tests by default; check the script) |
| Cargo | `cargo check` (fast type-check, no codegen), `cargo build` (full compile, no tests) |
| Go | `go build ./...` (no tests), `go vet ./...` (static checks, no codegen) |

Don't conflate "skip tests" with "the work is done" — the user still needs tests to pass before claiming done. The split is *fast feedback first, full verification before completion*.

#### Skip publish / docs / signing / verify phases

These run only when the user explicitly asks for them.

- **Maven**: don't run `deploy`, `release`, `site`, `gpg:sign`, `verify` (unless the user said so). `compile` / `package` / `install` are the defaults.
- **Gradle**: don't run `publish`, `publishToMavenLocal`, `release`, `javadoc`, `signArchives`, `check` (unless asked). `compileJava` / `assemble` / `build` are the defaults; `build` already includes tests, prefer `assemble` if you want only outputs.
- **npm / pnpm / yarn**: don't run `npm publish`, `npm pack`, `npm run docs`. `npm run build` and `npm install` are the defaults.
- **Cargo**: don't run `cargo publish`, `cargo doc`. `cargo check` / `cargo build` are the defaults.

#### Skip dependency refresh / offline mode default

Don't force a refresh of dependency caches unless something specifically calls for it.

| Tool | Forced refresh flag (avoid by default) | When justified |
|---|---|---|
| Maven | `-U` | Snapshot dependency just changed; cache says it's fresh but you know better. |
| Gradle | `--refresh-dependencies` | Same as above. |
| npm / pnpm / yarn | `npm ci` over `npm install` | CI / clean reproducible install; not for local iteration. |
| Cargo | `cargo update` | Explicitly bumping locked versions — don't run as part of routine builds. |

Plain `mvn install`, `./gradlew build`, `npm install`, `cargo build` use the cache. Trust the cache unless there's a specific reason not to.

## Per-tool notes

### Maven

- **Wrapper if present**: prefer `./mvnw` over `mvn` so the project's pinned Maven version is used.
- **Default for "verify a Java change compiles"**: `./mvnw compile -DskipTests` (or `./mvnw package -DskipTests` if the test code's compilation also matters).
- **Default for "is this PR ready"**: `./mvnw verify` — runs tests and integration tests. Note this *does* include the verify phase, but here it's the goal, not a default.
- **Multi-module reactor**: build only the affected module with `./mvnw -pl <module> -am compile` rather than the whole reactor when you know the change is local.

### Gradle

- **Wrapper if present**: prefer `./gradlew` over `gradle`.
- **Default for "verify a Java change compiles"**: `./gradlew compileJava` (no tests, no resource processing) or `./gradlew assemble` (full build outputs, no tests).
- **`build` task includes `test`** — use `assemble` if you want outputs without test execution.
- **Configuration cache and build cache are on by default in modern Gradle**; don't disable them unless you know why.

### npm / pnpm / yarn

- **Detect which one the project uses** by lockfile: `package-lock.json` → npm; `pnpm-lock.yaml` → pnpm; `yarn.lock` → yarn. Don't run a different one — you'll create a second lockfile and confuse the toolchain.
- **`install` after manifest changes; `ci` for clean reproducible installs.** `npm install` updates the lockfile; `npm ci` requires the lockfile to be up-to-date and is faster.
- **Build script names are project-specific.** `npm run build`, `npm run typecheck`, `npm run lint` — read `package.json#scripts` first.

### Cargo

- **`cargo check` is the right tool for "does it compile?"** — it skips codegen and is dramatically faster than `cargo build`.
- **`cargo build --release` only when you specifically want a release build.** Default is debug.

### Go

- **`go build ./...` builds everything; `go vet ./...` runs static checks; `go test ./...` runs tests.** Each is a separate command.
- **Modules**: `go mod tidy` after manifest changes; don't run as a default build step.

### Other tools (Make, Bazel, sbt, mix, etc.)

ASK before invoking. The conventions for what's "minimal" vary too much to assume — Bazel's `bazel build //...` is not analogous to `mvn install`. Get the project's preferred command from the user, the README, or the CI config rather than guessing.
